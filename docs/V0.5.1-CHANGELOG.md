# v0.5.1 — Stage 6 SQLCipher unlock (Track B)

> Internal-cutover changelog for the second half of the
> v0.5.0 roadmap. Track A (workspace split) shipped as
> v0.5.0; this release closes the last big connector gap —
> the TRAE SOLO conversation stash.

This release is **Track B** of the v0.5.0 roadmap published
in `docs/V0.5.0-ROADMAP.md`. It is **additive** on top of
v0.5.0: no schema bump, no IPC rename, no `awl-*` crate
change. The new connector lives entirely in `awl-core`
plus a new IPC handler in `awl-ipc`.

---

## 1. Why this ship

The pre-v0.5.1 build could read 10 of the 11 local agent
sources on a real macOS install. The eleventh — TRAE SOLO
(ByteDance, Electron-based) — was locked behind SQLCipher-4
encryption with the key held in the macOS keychain under
service `TRAE SOLO Safe Storage`. v0.5.0's Stage 6-P1 was
the explicit blocker on the public roadmap, and v0.5.1
removes it.

User-visible effect: once the user grants one
`security find-generic-password` GUI prompt (click
"Always Allow"), all TRAE SOLO conversation history
becomes searchable in the main timeline, just like the
10 other sources.

## 2. The connector

### 2.1 Where it lives

- `crates/awl-core/src/trae_solo.rs` — pure state machine
  + keychain access + decryption pipeline. No Tauri
  runtime dependency. No `rusqlite`-feature-conditional
  code. Tested by a self-contained round-trip that
  builds a fresh SQLCipher-encrypted DB and decrypts it
  with our helper.
- `crates/awl-core/src/connectors/trae_solo.rs` — the
  `Connector` trait implementation. Emits a
  `ScanReport` with the right `status` (`ok` /
  `failed` / `skipped`) and writes one `raw_events` row
  per TRAE SOLO message bubble.
- `crates/awl-ipc/src/lib.rs` — two new IPC commands:
  - `scan_trae_solo(sinceMs: Option<i64>)` — mirrors
    the other per-source scan handlers.
  - `trae_solo_status()` — read-only state probe used
    by the Home page card.

### 2.2 Decryption flow

The connector shells out to the homebrew `sqlcipher`
CLI (3.53.4 / SQLCipher 4.19.0 community) for the actual
decryption:

```rust
let key = derive_chrome_safe_storage_key(password, salt)?;
let dst = tmp.join("plaintext.db");
decrypt_to_plaintext(&src, &dst, &key)?;
let plain = Connection::open_with_flags(&dst, SQLITE_OPEN_READ_ONLY)?;
walk_messages_and_emit_raw_events(...);
```

The `decrypt_to_plaintext` helper runs a 4-statement
SQL script via sqlcipher's stdin:

```sql
PRAGMA key = "x'<hex-of-derived-key>'";
ATTACH DATABASE '<dst>' AS plaintext KEY '';
SELECT sqlcipher_export('plaintext');
DETACH DATABASE plaintext;
```

This is the canonical SQLCipher "decrypt a copy" recipe
— the destination file is a plain SQLite DB that the
existing `awl-db` `rusqlite` (no `bundled-sqlcipher`
feature) can read with no surprises.

The plaintext copy is written to `$TMPDIR/awl-trae-...`
and removed at the end of the ingest (both on success
and on early-error paths), so no decrypted blob lingers
on disk after the run.

### 2.3 Why CLI shelling, not `rusqlite` `bundled-sqlcipher`

The workspace already has `rusqlite = "0.32"` with
`features = ["bundled"]` everywhere. Adding
`bundled-sqlcipher` to the same `rusqlite` entry would
either:

1. Force the main `awl-db` to use SQLCipher too — which
   would break the existing `ledger.db` (no key set
   means every `SELECT` fails with a SQLCipher HMAC
   mismatch).
2. Conflict with feature unification: Cargo's
   `rusqlite = "0.32"` resolver unifies features across
   all dependents in the dep graph, so the moment
   `awl-core` enables `bundled-sqlcipher`, the rest of
   the workspace inherits it.

Both options break v0.5.0. CLI shelling sidesteps the
issue entirely: `sqlcipher` runs as a subprocess that
produces a plaintext file, and the rest of the
workspace keeps its plain-`rusqlite` link.

### 2.4 Chrome Safe Storage key derivation

Chrome (and Electron apps built on it, including
TRAE SOLO) derives the SQLCipher key from the
keychain password using:

- **PRF**: HMAC-SHA1
- **Salt**: `"saltysalt"` (legacy Chromium v10) or
  `"peanuts"` (Chrome 80+)
- **Iterations**: 1 (yes, one)
- **Output**: 16 bytes

The connector tries `"peanuts"` first and falls back
to `"saltysalt"` on `sqlcipher_export` failure. Both
attempts run inside a temp dir that's removed
afterward.

```rust
pub fn derive_chrome_safe_storage_key(
    password: &str,
    salt: &[u8],
) -> Result<[u8; 16], TraeSoloError> {
    let mut out = [0u8; 16];
    pbkdf2::pbkdf2_hmac::<sha1::Sha1>(
        password.as_bytes(),
        salt,
        1,
        &mut out,
    );
    Ok(out)
}
```

### 2.5 The five-state machine

The connector and the Home page card share one
`TraeSoloState` enum:

| Variant | Trigger | UI copy |
|---|---|---|
| `NoKeychainEntry` | `security find-generic-password` returned 44 (no item) | "未检测到 keychain 条目" (amber) — tells the user to launch TRAE SOLO once |
| `KeychainAccessDenied` | user clicked "Deny" on the GUI prompt | "keychain 访问被拒绝" (amber) — re-trigger via the "重新触发" button |
| `Unlocked { events_found }` | one of the two salt attempts produced a recognized schema | "已解锁 · N 条对话" (emerald) |
| `SchemaMismatch { detail }` | both salts produced a plaintext DB without a recognized table | "schema 不匹配" (red) |
| `Error { detail }` | sqlcipher CLI missing, file permissions, etc. | "错误: …" (red) |

The connector maps these to `ScanReport.status` as:

- `Unlocked` → `ok` (with `events_inserted` count).
- `NoKeychainEntry` / `KeychainAccessDenied` →
  `skipped` (no failure counted, no user-visible
  warning — just a `note` field in the auto-rescan
  log).
- `SchemaMismatch` / `Error` → `skipped` (still
  not a hard failure, but the `error` field is
  populated so the user can see the detail in
  the Sessions page).

`auto_rescan_all` was updated to treat
`connector not registered` and `no keychain entry`
as a graceful skip (INFO level, not WARN), so the
user's startup log stays clean even when TRAE
SOLO hasn't been launched yet.

## 3. UI changes

### 3.1 Home page card

`app/src/App.tsx` adds a new `Card title="TRAE SOLO
(SQLCipher)"` next to the existing "Status" card. It
polls `trae_solo_status` every 5 seconds and renders
one of the five states above. The card is purely
read-only — clicking the "重新触发" button calls
`scan_trae_solo` to retry a denied keychain prompt
or to refresh the count after a fresh TRAE SOLO
session.

### 3.2 Capabilities

No new permission was needed: the keychain access
goes through `security find-generic-password`,
which is its own OS-level prompt, not a Tauri
plugin permission. `capabilities/default.json`
is unchanged from v0.5.0.

## 6. User one-time setup

After installing v0.5.1, the user sees the Home
page card say "未检测到 keychain 条目". To
unlock:

1. **Launch TRAE SOLO at least once.** This
   creates the `TRAE SOLO Safe Storage` keychain
   entry. (This is something the user does
   naturally the first time they sign in.)
2. **Click the "重新触发" button on the Home
   page card.** This triggers a macOS GUI
   prompt:
   > Agent Work Ledger wants to access the
   > "TRAE SOLO Safe Storage" item in your
   > keychain.
   Click "Always Allow" to never see this
   again.
3. The card flips to "已解锁 · N 条对话",
   and the next `auto_rescan_all` tick picks
   up the new rows.
