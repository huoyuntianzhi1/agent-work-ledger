# v0.5.0 — Roadmap

> The first version that breaks the single-crate shape and the
> transparent-at-rest storage model. Two parallel tracks; both must
> ship before tagging v0.5.0.

## Goal

1. **Workspace split** — turn `app/src-tauri/src/lib.rs` (2 423
   lines, 30+ `#[tauri::command]`, 21 modules) into 4 domain crates
   + 1 desktop binary crate. The split is purely structural; the
   user-visible behaviour of the binary does not change.
2. **Stage 6 SQLCipher unlock** — read the TRAE SOLO
   `ai-agent/database.db` file, which is the last sizeable
   conversation stash on a real macOS install that we currently
   *cannot* read. Adds a new connector and (transparently) a new
   storage mode for the user's existing on-disk DB.

## Non-goals (deferred to v0.5.1+)

- Adding more connectors that require keychain (other VSCode
  forks with `* Safe Storage` entries).
- A cloud LLM provider. Still on hold — bolting one in requires
  the redactor contract to be enforced at the IPC layer, which
  is its own audit.
- A SQLCipher-key rotation flow. Day-one assumes the key from
  the user's keychain is permanent; rotation would invalidate
  every existing `raw_events` row encrypted under the old key.

## Track A — Workspace split (≈ 90 min)

**Current state**: `app/src-tauri/` is a single Cargo crate with
20 sub-modules, 30+ `#[tauri::command]` in `lib.rs`, and 77
`use crate::` paths. Maintainable but the IPC layer is the
biggest single contributor to `lib.rs` line count.

**Target structure**:

```
app/src-tauri/
├── Cargo.toml                      # [workspace] + member list
└── crates/
    ├── awl-core/                   # domain logic (no Tauri dep)
    │   └── src/{connectors/, redactor.rs, idb.rs, ai.rs,
    │            eisenhower.rs, brief.rs, planner.rs, search.rs,
    │            etl.rs, summary.rs, reports.rs, error.rs}
    ├── awl-db/                     # schema + retention + window_state
    │   └── src/{app_settings.rs, retention.rs, window_state.rs,
    │            lib.rs (open_db / migrate / migrate_for_tests)}
    ├── awl-export/                 # bulk JSON / CSV / zip-of-MD
    ├── awl-ipc/                    # all #[tauri::command] + AppState
    └── awl-desktop/                # Tauri shell + main + tauri.conf.json
        └── src/{main.rs, lib.rs (run / setup / tray / window event)}
```

**Estimated work**:

- Move 21 `.rs` files into the 4 domain crates. Already done in
  the v0.4.10 WIP commit (`6bd015b`, since `git reset --hard`'d);
  the file moves were the cheap part.
- Re-write 77 `use crate::` paths to point at the right crate.
  Most of these are intra-`awl-core` (no change needed because
  the crate root absorbs them). The 6 cross-crate `use`s
  (`awl-db` → `awl-core::error`, `awl-export` → `awl-core::*`)
  have been done in the same WIP; need to re-verify on the
  current tree.
- Split `lib.rs` into `awl-ipc::lib.rs` (all commands + `AppState`
  + input/output structs) and `awl-desktop::lib.rs` (just
  `pub fn run()` + the setup closure + tray + window event
  handlers). This is the bulk of the work — 30+ commands, ~1 800
  lines of the existing 2 423.
- Move `tests/capabilities_lint.rs` and the integration tests
  into `awl-desktop/tests/`, since they exercise the full IPC
  surface.
- 5 new `Cargo.toml` files with the right `awl-* = { path = ... }`
  dependencies. Done in the same WIP.

**Risk**: the WIP commit had a partial lib.rs split that didn't
compile. Before re-attempting, I want to re-derive the split from
the current `lib.rs` rather than re-applying the WIP.

**Verification**:

- `cargo check --workspace` — all 5 crates compile, no
  dead-code warnings on `awl-core` (it doesn't import Tauri).
- `cargo test --workspace` — same 138-test count, no new
  `unused_import` warnings.
- `pnpm tauri build` — bundle size 7.10 MiB ± 50 KB (we expect
  a small uptick from `awl-ipc` carrying its own
  `tauri::generate_handler!` macro instantiation; offset by
  `awl-core` no longer linking Tauri at all).
- Manual: launch the .app, click through Home / Timeline /
  Sessions / Planner / Settings, confirm no behavioural change.

## Track B — Stage 6 SQLCipher (≈ 4–6 hours, includes user wait)

**Current state**: TRAE SOLO's
`~/Library/Application Support/TRAE SOLO/ModularData/ai-agent/database.db`
is a 610 KB SQLCipher-4-encrypted SQLite file. It is the only
remaining large conversation stash on a real macOS install
that we cannot read — the on-disk encryption is at rest, not in
the schema, so the existing `rusqlite` build cannot open it.

**Target**: add a new `trae_solo` connector that

1. Locates the keychain entry for TRAE SOLO (the service name
   is `${Product} Safe Storage`, e.g. `TRAE SOLO Safe Storage`).
2. Prompts the user once to authorise `security find-generic-password`
   to return the key bytes.
3. Calls `PRAGMA key = "x'<hex_key>'"` on a fresh `Connection`,
   then runs `.tables` to confirm decryption.
4. Walks the `messages` / `composerData` tables (TBD once we
   see the schema) and ingests the rows through the same
   `raw_events` pipeline as the other 10 connectors.

**Pre-flight check (already done)**:

- SQLCipher 4.19.0 is installed via Homebrew
  (`/opt/homebrew/Cellar/sqlcipher/4.19.0/lib/libsqlcipher.a`).
- `rusqlite` is already in `Cargo.toml` with the `bundled`
  feature, which compiles SQLite from source. To support
  SQLCipher, swap to `rusqlite = { version = "0.32", features
  = ["bundled-sqlcipher"] }` — but that requires a
  `SQLCIPHER_BUNDLED=1` build env, which our release profile
  would need to set. The simpler path is `sqlcipher = "0.2"`
  (the standalone crate) with a thin `Connection` shim; the
  even simpler path is `rusqlite` with `bundled-sqlcipher`
  plus a patched `build.rs` that points at the system
  `libsqlcipher.a`.

**Decision points for 王总**:

- **(B1) Ship the SQLCipher keychain access in a `keyring`
  crate, or hand-roll `security` CLI calls?** A `keyring` crate
  pulls in an extra dep and has a buggy track record on macOS
  Sonoma+; `security find-generic-password` is one binary call,
  no native lib, more reliable. **Recommendation: hand-roll.**
- **(B2) Cache the key on disk, or prompt every launch?** A
  cached key is a new secret on disk; a fresh prompt is a
  one-time-per-launch UX hit. **Recommendation: prompt once
  per launch, in the first time the user opens Sessions after
  the connector is enabled, then forget.**
- **(B3) When the user denies the keychain prompt, what do
  we do?** Three options: (a) silently skip the connector
  with a yellow "需要授权" badge; (b) re-prompt every launch
  until they accept; (c) add a settings toggle to disable
  the connector entirely. **Recommendation: (a) + (c) together.**

**Estimated work**:

- 30 min: dependency selection + `build.rs` patching if
  needed.
- 1 hour: `awl_core::connectors::trae_solo` connector,
  mirroring the `cursor` connector's shape (read plaintext-
  in-SQLite for the simple path, gated by `if sqlcipher_key.is_some()`).
- 30 min: `keychain::key_for(service: &str) -> Option<Vec<u8>>`
  helper, wired into the connector's first-call path.
- 30 min: Home page + Sessions page UI to surface the
  "TRAE SOLO 需要授权" state.
- 1 hour: integration test that uses a known-key SQLCipher
  file (write a fixture, encrypt it, decrypt it via the
  connector, assert on the rows).
- 30 min: privacy / redactor pass — every value pulled from
  the encrypted DB must still go through `Redactor::global()`
  before it hits `raw_events`. Same guarantee as every other
  connector.
- Plus ~30 min: rebuild + re-sign + reinstall + `--scan-once`
  end-to-end verification.

**Risk**:

- The TRAE SOLO keychain service name is a guess from
  empirical observations of other VSCode forks
  (`Cursor Safe Storage` was the pattern that worked for
  Cursor's plaintext stash — different mechanism, same
  convention). If TRAE SOLO uses a different service name
  the connector will be a 30-minute exercise in `security
  dump-keychain` + grep.
- The `messages` / `composerData` table schema inside
  SQLCipher-4 encryption is unknown until the key is
  recovered. The connector's first draft will have to be
  exploratory.

## Sequencing

The two tracks are independent but share the rebuild + re-sign
+ reinstall + `--scan-once` verification at the end. I propose:

1. **Track A first** (workspace split). It is pure refactor
   and gives us 5 isolated build targets — a SQLCipher build
   failure later won't take down the rest of the project.
2. **Track B second** (Stage 6). It needs the user to run
   one keychain prompt, which is best done as the final
   step before tagging.
3. **Tag v0.5.0** once both tracks pass `cargo test --workspace`
   and `--scan-once` shows a non-zero `trae_solo` row count.

## What ships in v0.5.0

- 5-crate workspace (Track A)
- `trae_solo` connector reading from the encrypted DB
  (Track B)
- 1 new `raw_events` row per TRAE SOLO conversation bubble
- New `connectors/trae_solo.rs` in `awl-core`
- New Home-page card showing the connector's status
  (loaded / needs-key / disabled)
- CHANGELOG entry, README connector table bumped to 12,
  "What's new" section in the README

## What does NOT ship in v0.5.0

- A cloud LLM provider.
- SQLCipher encryption of AWL's own `ledger.db` (we *read*
  SQLCipher, we don't *write* it).
- `awl-crypto` / `awl-keychain` standalone crates — these
  are nice-to-have structure but the helper fits in
  `awl-core` for now and a refactor to split them out is
  a one-day follow-up if the keychain code grows.
